00 / 개요

새 모바일 오더 서비스를 운영하기 위한 관리 시스템.

DoubleNC가 카페 대상 모바일 오더 서비스로 사업을 확장하면서 주문·매출을 확인할 관리 시스템이 필요해졌어. 기존 기프티콘 거래 서비스와는 별도의 신규 서비스였어.

비즈니스 목표
신규 모바일 오더 서비스의 운영 현황을 확인하고, 영업과 매장 운영을 지원할 관리 기반 만들기.
시작 조건
명확한 요구사항·설계 가이드가 없는 상태에서 운영진·영업팀·카페 점주의 서로 다른 목적을 조율해야 했어.
배포 제약
빠른 결과물 확인 요구가 있어, 모든 기능을 한 번에 구현하기보다 첫 배포 범위를 정해야 했어.

서로 다른 사용자에게 필요한 정보를 제공하면서, 무엇부터 배포해야 할까?

회사 운영진은 전체 현황을, 카페 점주는 자기 매장 정보를 확인해야 했고 영업팀에도 서비스 소개를 위한 정보가 필요했어. 명확한 요구사항이 없는 초기 단계에서 정보 구조·접근 권한·첫 배포 범위를 정하는 것이 내 역할이었어.

01 / 출발점

누구의 어떤 업무를 지원할지 먼저 정했어.

회사·영업팀·점주는 같은 정보를 보려는 게 아니었어.

회사는 전체 서비스의 성과를, 영업팀은 고객에게 설명할 정보를, 점주는 자기 매장의 주문과 매출을 확인해야 했어.

초기 요구사항이 명확하지 않아, 기능 목록보다 각 사용자의 업무 목적을 먼저 정리했어.

어떤 요구를 함께 고려했나?

빠른 결과물을 원하는 일정 속에서 모든 요구를 한 번에 구현하기는 어려웠어. 정보 구조뿐 아니라 첫 배포에 포함할 범위도 정해야 했지.

권장 구도

증명할 판단

자료 조건
개인정보·매출 자료 비식별화. 근거 없는 대기 시간·요청 건수 추가 금지.
★ v1.4 · Problem Evidence ★

운영·영업팀이 개발팀에 수치를 요청해야 했던 실제 업무 사례 하나를 확보해. 요청자·필요 정보·지연의 사업적 영향·당시 전달 경로를 연결하고 요청 건수나 소요 시간은 임의로 만들지 마.

02 / 발견과 첫 판단

데이터보다, 데이터를 받는 경로가 문제였어.

운영 수치를 확인하려면 개발팀의 추출·전달을 거쳐야 했어.

정보를 직접 확인할 수 없어, 요청자와 개발팀 사이에 데이터 추출·전달 과정이 반복됐어.

그래서 어떤 수치를 보여줄지뿐 아니라 누가 직접 확인할 수 있어야 하는지를 설계 기준으로 삼았어.

정보를 고를 때 본 기준

반복적으로 요청되는 정보인지, 먼저 확인해야 할 정보인지, 누가 접근할 수 있어야 하는지를 함께 고려했어. 요청 빈도나 소요 시간의 정량 기록은 현재 확인되지 않았어.

방법의 등장 배경 · 데이터의 존재에서 접근 가능성으로

중요한 건 데이터가 있느냐보다, 누가 어떤 일을 위해 확인해야 하느냐였어.

왜 이 접근이 필요했나

개발팀에 수치를 매번 요청하는 방식은 화면 하나의 문제가 아니라 업무 흐름의 문제였어. 모든 수치를 한 화면에 올려도 역할별 요구는 해결되지 않을 수 있어.

어떻게 적용했나

운영진·영업팀·점주가 해야 할 업무와 필요한 정보를 대응시켰어. 회사 전체 현황과 개별 매장 정보를 구분하고, 역할별 접근 범위를 설계했지.

무엇을 선택하고 포기했나

전체·상세를 나누면 정보 해석은 쉬워지지만 화면 이동 단계가 늘어나. 접근 권한 설계도 복잡해져. 실제 첫 출시의 우선순위 결정은 원본 자료로 확인해야 해.

역할 → 업무 → 정보 구조는 당시 설계를 설명하기 위한 분석 틀이야. 실제로 공식 워크숍을 진행했거나 복잡한 권한 시스템을 구현했다는 주장과는 구분해야 해.

당시 운영·영업·점주의 실제 요청이나 회의 기록, 어떤 의사결정을 위해 데이터를 확인해야 했는지, 원래 데이터 전달 경로를 붙여줘. 역할별 실제 권한표와 대표 업무 예시도 필요해.

★ v1.5 · SOURCE NEEDED ADM-02

실제 첫 출시한 기능과 보류한 기능을 최소 한 쌍으로 적어줘. 당시 우선순위 근거, 구현 제약, 실제 배포 화면·기록까지 연결해. 추정한 출시 계획을 당시 사실처럼 쓰지 말아줘.

03 / 핵심 선택

전체 현황과 매장 상세를 분리했어.

전체 상태를 먼저 보고, 필요한 매장으로 들어가도록 했어.

메인 화면은 전체 운영 현황에 집중하고, 개별 매장의 정보는 상세 화면에서 확인하도록 구조화했어.

점주에게는 자기 매장의 데이터만 허용했어. 한 화면의 정보량을 줄이는 대신, 전체 파악과 매장 관리의 목적을 분리한 거야.

선택의 기준과 감수한 점

하위 화면으로 들어가는 단계는 생기지만, 전체 정보와 매장 정보를 한 화면에서 해석해야 하는 부담을 줄이는 방향을 택했어. 아래 비교는 당시 판단을 설명하기 위한 재구성이며, 실제 대안 시안이 확인된 것은 아니야.

결정의 근거 · 정보 구조

서로 다른 업무는 서로 다른 정보와 접근 범위를 요구했어.

논리적 비교 대안

모든 운영 정보를 하나의 화면에

상세 이동은 줄지만 전체 사업 현황과 매장 관리의 정보가 뒤섞여. 실제 당시 시안이 확인된 대안은 아니라 설명용 비교야.

선택한 구조

전체 현황 → 매장별 상세

서비스 전체 판단과 점주 업무를 구분하고 역할별 접근 권한을 반영해. 대신 상세 진입 단계가 늘고 권한 설계가 복잡해져.

결정 후 확인된 산출: 이 정보 구조를 바탕으로 관리 시스템을 설계·배포했어. 정보 확인 시간이나 요청 감소·만족도는 측정하지 않았어.

★ v1.4 · Alternative & Role Evidence ★

실제 역할·권한 표와 요구사항·화면 자료를 확보해. 원본 대안 시안이 없는 한 ‘모든 정보를 한 화면에’는 논리적 비교로 표기해. 실제 구현한 권한 범위도 확인해야 해.

04 / 다음 판단

모든 요구를 한 번에 출시하지 않았어.

주요 기능을 먼저 배포하고, 이후 요구를 반영하는 방향을 택했어.

개발·데이터 담당자들과 구현 범위와 진행 순서를 조율했어.

영업팀에도 먼저 필요한 기능을 제공하고, 실제 영업 과정에서 추가 요구를 수집하는 방향으로 논의했지.

아직 근거를 보완해야 하는 부분

최초 배포와 후속 기능의 정확한 목록은 현재 자료로 확인되지 않아. 구체적인 기능 한 쌍이 확보되기 전까지, 우선순위 판단을 입증한 완성된 사례로 보기는 어려워.

05 / 제품에 반영

정보 구조와 권한을 관리 화면에 반영했어.

전체 → 매장 상세 구조로, 필요한 정보를 직접 찾도록 했어.

회사는 운영 현황에서 개별 매장으로 들어가고, 점주는 허용된 자기 매장 정보를 확인하는 구조를 설계했어.

아래는 그 구조를 설명하는 재구성이야. 실제 배포 화면은 아니야.

화면을 볼 때 확인할 부분

전체 상태를 보는 화면과 매장별 정보를 탐색하는 화면의 관계가 핵심이야. 현재 예시 화면만으로 당시 구현과 사용성을 검증할 수는 없어.

06 / 결과와 한계

관리 시스템을 배포했어. 시간 절감은 미측정이야.

확인된 결과는 운영 정보에 접근할 수 있는 시스템을 만든 것이야.

신규 모바일 오더 서비스의 관리 시스템을 설계하고 단계적으로 배포했어.

개발팀을 거쳐 받던 정보를 직접 확인하도록 만드는 데 집중했어. 요청 감소량과 운영 시간 단축은 측정 자료가 없어 확인할 수 없어.

이 케이스가 보여주는 판단

무엇을 많이 보여줄지보다, 누가 어떤 목적으로 정보에 접근해야 하는지를 구조화한 경험이야. 제품의 구현과 운영 효과는 구분해서 봐야 해.

다시 한다면 · 다음 검증 제안

적절한 사람이 필요한 정보를 실제로 빠르게 찾는지 검증하겠어.

운영진·영업팀·점주 각각의 업무 과제를 정하고 정보 탐색 시간, 잘못된 권한 접근, 여전히 개발팀에 요청하는 업무를 확인하겠어. 기능 확대 전에는 개발자와 권한을 검증할 거야. 당시 측정한 결과가 아니라 다음 검증 계획이야.

★ v1.4 · Outcome ★

실제 첫 배포 범위·배포 기록·역할별 권한 구현을 확인해. 업무 효율·개발팀 요청 감소·시간 절감은 근거 없이 성과로 쓰지 마.

인사이트 · 다음 제품에도 적용할 판단

정보가 있어도 필요한 사람이 활용할 수 없다면 충분하지 않아.

다른 운영 제품에서도 대시보드에 지표를 채우기 전에 누가 언제 어떤 업무를 위해 정보를 찾는지부터 살펴볼 거야. 실제로 스스로 필요한 답을 찾고 권한을 안전하게 지키는지 검증하겠어. 화면을 만들었다는 사실만으로 업무 효율이 좋아졌다고 주장하진 않을 거야.

자료의 범위

화면·도표는 설명용 재구성이야. 실제 배포 화면과 리서치 원본은 추가해야 해. 확인된 구현 경험과 아직 검증되지 않은 사용자 효과를 구분했어.
